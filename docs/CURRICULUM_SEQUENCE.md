## Phase 1: Programming, SQL and databases (months 1–3)

Write, test and debug real Python against a real PostgreSQL database, without leaning on an AI assistant to explain it.

**Exit gate:** Independently understand, modify, debug and test a small application you wrote.

| Runs through this phase | |
|---|---|
| Security | Secrets in environment variables, never in code; parameterised queries. |
| Testing | pytest from the first validator onward. |
| Git | Every exercise lives in a repository with feature branches. |
| Documentation | A README that lets someone else run your project. |
| Architecture | Why separate parsing, validation and storage. |

### Programming

**Python foundations**

- Why: Everything later is built in Python, and you need to read and fix it yourself, not only prompt for it.
- Finance: Replace a VBA macro: read a GL extract, total by account and write a report.
- Needs: nothing before it
- Subtopics (9): Python fundamentals where gaps exist; Data structures and collections; Functions and modular programming; Exception handling; File handling; JSON processing; Virtual environments; Reading error messages and tracebacks; Writing code without an AI assistant

**Python engineering**

- Why: Moves you from scripts that work once to software that others can trust and change.
- Finance: Model ledger and budget lines as typed classes that validate themselves.
- Needs: Python foundations
- Subtopics (9): Object-oriented programming; Classes, inheritance and composition; Type hints; Modules and packages; Decorators and generators concepts; Dependency management; Async programming fundamentals; Environment variables; Application configuration

### Engineering habits

**Software engineering**

- Why: Version control, tests and debugging are what separate an engineer from someone generating code.
- Finance: Test a variance calculation against a hand-checked month, so a change cannot silently alter a reported number.
- Needs: Python foundations
- Subtopics (11): Git and GitHub; Branching and merging; Project structure; Debugging; Logging; pytest; Fixtures; Parameterised tests; Mocking; Code quality; Reading and reviewing AI-generated code

### Databases

**SQL and database foundations**

- Why: Finance data lives in relational systems, and every later phase queries it.
- Finance: Find unmatched transactions with an anti-join and build running balances with window functions.
- Needs: Python foundations
- Subtopics (12): SQL fundamentals and advanced querying; Joins and anti-joins; Aggregations; CASE and NULL handling; CTEs and subqueries; Window functions; PostgreSQL; Relational data modelling; Keys and constraints; Transactions; Indexing fundamentals; Database connectivity

## Phase 2: Data engineering and finance analytics (months 4–7)

Take raw GL, budget and forecast data to a validated model and a working FP&A report.

**Exit gate:** Run a reproducible pipeline from raw extracts to a Power BI report, and prove its totals reconcile to source.

**Projects:** P1 Finance Data Foundation; P2 FP&A and Commercial Intelligence

| Runs through this phase | |
|---|---|
| Security | Synthetic or anonymised data only; row-level security in Power BI. |
| Testing | Data validation rules and reconciliation checks that fail loudly. |
| Git | Pipelines and notebooks under version control. |
| Documentation | A data dictionary and a lineage note for every model. |
| Architecture | Choosing PostgreSQL or Databricks for a workload, and saying why. |

### Data wrangling

**Pandas for finance data**

- Why: The everyday tool for cleaning and shaping data before it reaches a model or a database.
- Finance: Reshape a messy trial balance and join it to a chart of accounts.
- Needs: Python engineering, SQL and database foundations
- Subtopics (7): Selective pandas for loading and checking data; DataFrames and indexing; Cleaning and type conversion; Merging and reshaping; Grouping and aggregation; Dates and period handling; Pandas or SQL: choosing the right tool

**Data ingestion and validation** (new) · P1

- Why: An AI system is only as trustworthy as the data pipeline underneath it.
- Finance: Load GL actuals, budgets and forecasts, rejecting rows that break accounting rules.
- Needs: Pandas for finance data, Software engineering
- Subtopics (6): Extract, load and transform; Incremental loads; Schema validation; Data quality rules; Reconciliation checks; Pipeline logging and reruns

### Finance data platform

**Finance data modelling** (new) · P1

- Why: Good models make every report and AI answer simpler and more correct.
- Finance: Design facts and dimensions for GL, budget, forecast, entity, cost centre and period.
- Needs: Data ingestion and validation
- Subtopics (6): Facts and dimensions; Star schemas; Chart of accounts hierarchies; Slowly changing dimensions; Actuals, budget and forecast versions; Currency and period conventions

**Databricks and PySpark** (new)

- Why: Enterprises run data at a scale a laptop and pandas cannot, and this is the primary platform in your stack.
- Finance: Rebuild the GL pipeline as bronze, silver and gold tables.
- Needs: Finance data modelling
- Subtopics (6): Distributed processing concepts; Databricks workspace and notebooks; PySpark DataFrames; Delta tables; Medallion architecture; Jobs and scheduling

### Finance analytics

**Power BI** (new) · P2

- Why: It is how finance leaders actually see your work, and the model behind it is real engineering.
- Finance: Build an actual-versus-budget report on your own semantic model.
- Needs: Finance data modelling
- Subtopics (6): Power Query transformations; Semantic models and relationships; DAX measures; Time intelligence; Report design for finance; Row-level security

**FP&A and commercial analytics** (new) · P2

- Why: This is where your finance judgement becomes a differentiator nobody else can copy.
- Finance: Explain margin movement through price, volume and mix.
- Needs: Power BI
- Subtopics (6): Variance analysis in code; Price, volume and mix; Forecasting methods; Forecast accuracy; Customer profitability; Margin analytics

## Phase 3: Applied AI and RAG (months 8–11)

Build a finance knowledge assistant that answers from approved documents with citations you can check.

**Exit gate:** Demonstrate retrieval quality, source grounding, access-aware search and measured answer quality.

**Projects:** P3 Finance Knowledge Assistant

| Runs through this phase | |
|---|---|
| Security | Prompt injection basics and access-aware retrieval. |
| Testing | Prompt test sets and retrieval evaluation. |
| Git | Prompts are versioned like code. |
| Documentation | Record what each model call costs and why it was chosen. |
| Architecture | When RAG is the right answer, and when it is not. |

### LLM foundations

**LLM engineering**

- Why: You need to call models deliberately, knowing what they cost and how they fail.
- Finance: Generate a variance commentary as schema-validated output with its cost logged.
- Needs: Python engineering, Data ingestion and validation
- Subtopics (17): LLM architecture and fundamentals; Tokens and context windows; Model selection; Temperature and sampling; Context limitations; Model cost and latency; OpenAI APIs; API authentication; Streaming; Structured outputs; JSON schemas; Function calling; Tool calling; Provider abstraction; Model error handling; Rate limits; Azure OpenAI

**Prompt and context engineering**

- Why: Reliable output comes from the context you construct, not from clever wording.
- Finance: Write a tested prompt for variance analysis using real close scenarios.
- Needs: LLM engineering
- Subtopics (8): System instructions; Prompt structure; Few-shot prompting; Context construction; Output constraints; Grounding; Prompt testing; Prompt injection fundamentals

### Serving AI

**API essentials**

- Why: P3 needs an access-controlled service and P4 needs tools, so the basics cannot wait for phase 5.
- Finance: Expose variance results through a validated FastAPI endpoint.
- Needs: Python engineering, SQL and database foundations
- Subtopics (8): HTTP fundamentals; REST architecture; FastAPI; Pydantic; Request and response validation; API routing; Error handling; API testing

### Knowledge systems

**Knowledge ingestion** · P3

- Why: Retrieval cannot recover what ingestion lost.
- Finance: Ingest accounting policies and close checklists with source and owner metadata.
- Needs: Python engineering, LLM engineering
- Subtopics (6): PDF extraction; Document processing; Text normalisation; Metadata extraction; Document ingestion pipelines; Excel, CSV and structured-data ingestion

**Retrieval engineering** · P3

- Why: Answer quality is mostly retrieval quality, and it can be measured.
- Finance: Measure which chunking finds the right policy paragraph most often.
- Needs: SQL and database foundations, Knowledge ingestion
- Subtopics (9): Embeddings; Vector representations; Similarity search; Chunking strategies; Metadata filtering; PostgreSQL with pgvector; Semantic search; Hybrid search; Reranking fundamentals

**RAG architecture** · P3

- Why: A finance answer without a checkable source cannot be trusted.
- Finance: A policy assistant that cites the paragraph, respects entity access and refuses when unsure.
- Needs: Retrieval engineering, Prompt and context engineering, API essentials
- Subtopics (9): Retrieval pipelines; Context assembly; Grounded generation; Source citations; Document references; Access-aware retrieval; Retrieval quality; RAG evaluation; Failure analysis

## Phase 4: AI agents and evaluation (months 12–15)

Build a stateful finance agent with controlled tools, human approval and measured quality.

**Exit gate:** Demonstrate an observable agent workflow with persistence, human approval and repeatable evaluation.

**Projects:** P4 Finance Workflow Agent

| Runs through this phase | |
|---|---|
| Security | Tool permissions, approval gates and audit trails. |
| Testing | Agent tests, failure injection and regression evaluation. |

| Documentation | A design note for each agent: what is fixed, what is agentic, where a human approves. |
| Architecture | Workflow or agent: deciding, and defending the decision. |

### Agents

**Agent engineering** · P4

- Why: Most tasks need a workflow, not an agent, and knowing the difference is architecture.
- Finance: Design a variance investigation: fixed steps, agentic steps and human approval.
- Needs: RAG architecture
- Subtopics (11): Workflows versus agents; Agent loops; Planning and execution; Tool selection; Tool calling; State management; Context management; Memory; Human-in-the-loop; Workflow orchestration; Failure recovery

**LangGraph** · P4

- Why: Real work is long-running and interruptible, so state has to survive.
- Finance: A reconciliation agent that pauses for approval and resumes after a crash.
- Needs: Agent engineering
- Subtopics (10): Nodes and edges; Graph state; Conditional routing; Checkpointing; Persistence; Interrupts; Human approval; Long-running workflows; Recovery and resumability; Agent testing

**MCP**

- Why: A standard way to give agents tools, inside permission boundaries.
- Finance: Read-only ledger lookups, and a separately permissioned proposal tool.
- Needs: API essentials, Agent engineering
- Subtopics (9): MCP architecture; Hosts, clients and servers; Tools; Resources; Prompts; Server development; Client integration; Authentication and permission boundaries; MCP integration with applications and agents

**Reliable agent execution** · P4

- Why: In finance an agent must never act twice or act unapproved.
- Finance: An audit trail for every action, sufficient for a controller's review.
- Needs: LangGraph, MCP
- Subtopics (8): Tool permissions; Approval gates; Input validation; Idempotency; Retries; Audit trails; Safe execution; Failure handling

### Evaluation

**AI observability**

- Why: You cannot improve or defend what you cannot see.
- Finance: Show cost, latency and tokens per reconciliation run.
- Needs: LLM engineering
- Subtopics (8): Tracing; Prompt versioning; Token usage; Cost tracking; Latency monitoring; Error analysis; Performance monitoring; LangSmith

**AI evaluation** · P4

- Why: Quality has to be measured against datasets and thresholds, not impressions.
- Finance: A golden dataset of past variances that blocks a worse prompt.
- Needs: RAG architecture, LangGraph, AI observability
- Subtopics (10): Evaluation fundamentals; Golden datasets; Test-case design; Deterministic evaluation; LLM-as-judge; RAG evaluation; Agent trajectory evaluation; Regression testing; Quality thresholds; Evaluation automation

**Advanced RAG and agent design**

- Why: With evaluation in place, you can improve quality and prove it.
- Finance: Improve one measured metric while holding cost per close run flat.
- Needs: RAG architecture, AI evaluation
- Subtopics (9): Retrieval optimisation; Hybrid retrieval; Reranking; Query transformation; Agent evaluation; Workflow optimisation; Human approval design; Tool reliability; Cost and latency optimisation

Run a secured, integrated solution on Azure through a repeatable delivery pipeline.

### Production backend

**Backend engineering**

- Why: Moves your API from a demo to something that survives real use.
- Finance: Idempotent imports, so re-posting a journal file cannot double-count it.
- Needs: API essentials
- Subtopics (10): Dependency injection; SQLAlchemy; Alembic; Authentication; OAuth2; JWT; OIDC fundamentals; Webhooks; Retries; Idempotency

**Security**

- Why: Finance data is sensitive, and LLMs add new ways for it to leak.
- Finance: Plant an injection in a policy document and prove the assistant ignores it.
- Needs: Backend engineering, RAG architecture
- Subtopics (11): OWASP LLM Top 10; Direct prompt injection; Indirect prompt injection; Sensitive data exposure; Data leakage; RBAC; Least privilege; Secrets management; Input and output validation; Access-controlled retrieval; Audit logging

**Enterprise integrations** · P5

- Why: Real value sits in the systems a business already runs.
- Finance: Connect to an ERP-style extract with service-to-service authentication.
- Needs: Backend engineering, Security
- Subtopics (7): Identity providers; External APIs; Webhooks; Business application integrations; Enterprise data sources; Permission-aware tool access; System-to-system communication

### Delivery and cloud

**Deployment foundations**

- Why: Nothing delivers value while it runs only on your laptop.
- Finance: Run the reconciliation stack in containers and rehearse a restore.
- Needs: Software engineering, Backend engineering
- Subtopics (9): Linux and CLI fundamentals; Docker; Containerisation; Environment configuration; Cloud deployment fundamentals; CI/CD fundamentals; Automated testing before deployment; Application monitoring; Basic recovery procedures

**Cloud and production** · P5

- Why: Azure is your primary cloud, and owning production is the job.
- Finance: Deploy with separate dev and prod, then roll back on purpose.
- Needs: Deployment foundations
- Subtopics (11): Azure fundamentals; Azure Container Apps; Managed PostgreSQL; GitHub Actions; CI/CD pipelines; Environment separation; Secrets management; Deployment strategies; Rollbacks; Production monitoring; Azure architecture patterns

**Infrastructure as code** (new) · P5

- Why: Repeatable environments are how you pass audit and recover quickly.
- Finance: Rebuild the finance environment from code, with every change reviewed.
- Needs: Cloud and production
- Subtopics (5): Terraform fundamentals; State and backends; Modules and environments; Azure resources with Terraform; Reviewing and applying changes

### Operating the system

**Telemetry and monitoring** (new) · P5

- Why: Production problems must be seen across the whole system, not only the model.
- Finance: Trace one month-end run from upload to answer.
- Needs: Deployment foundations, AI observability
- Subtopics (5): OpenTelemetry fundamentals; Traces, metrics and logs; Instrumenting a FastAPI service; Dashboards and alerts; Service-level objectives

**Reliability engineering**

- Why: A close cannot wait because a model provider is down.
- Finance: Fall back cleanly during a simulated outage at month end.
- Needs: Deployment foundations, Reliable agent execution
- Subtopics (10): Retries and backoff; Idempotency; Timeouts; Rate limiting; Model fallback; Circuit breakers; State recovery; Backups and restores; Incident handling; Operational runbooks
